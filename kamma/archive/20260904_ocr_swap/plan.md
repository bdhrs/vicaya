# Plan: swap the OCR backend to ocrmypdf + wire in diacritic restoration

Spec: `spec.md`. Evidence: `kamma/threads/20260903_ocr_bakeoff/measurements.md` and `swap_scope.md`. No GitHub issue.

## Architecture Decisions

- **Replace the body, keep the seam.** `_extract_pdf_ocr_fallback(path) -> ExtractedText | None` stays as the entry point with the same name and signature. Everything behind it is replaced. This keeps the refresh loop, the status contract and the kill switch untouched, so the diff is confined to one function's implementation plus deletions.
- **Delete rather than disable.** The worker subprocess, framed stdout protocol, per-chunk timeouts and reader thread exist only to contain a deadlock in a library being removed. Leaving them dormant leaves the next reader wondering which path is live.
- **Restoration is a separate module on the quote path.** It does not touch extraction, the index, or `library_folders.py`. Search never needed it; only quoting does. Keeping it separate means the swap can ship without it and vice versa.
- **The status vocabulary is a cross-file contract.** `skill/vicaya/SKILL.md`, `README.md` and the `justfile` all read the `ocr` statuses. Any change to what statuses are emitted updates all of them in the same commit.
- **No mocks near a timeout, stall, or failure path.** The original deadlock passed 452 tests because a fake `close()` returned immediately. New failure-path tests spawn real processes.

- 2026-09-04 — **The swap shipped the slower of the two measured configurations, and the user caught it, not the plan.** The bake-off's headline **0.433 s/page → 1.32 days** is measured at **4 books × `--jobs 4`** (16 concurrent tesseract workers, `measurements.md:154` and `:171`). `refresh()` processes books **sequentially**, which is the *other* row of that same table: **0.904 s/page** (`:153`), projecting ~66 h rather than 31.7. T9 even says "at 4 books × `--jobs 4`" without observing that the refresh loop cannot do that.
- 2026-09-04 — **Fixed by raising `--jobs` rather than making the refresh loop concurrent.** ocrmypdf parallelises per page, so one invocation can use the whole machine; a concurrent-book loop would mean reworking the clock-based commit and the progress bar for no extra throughput. Measured live on the user's own run rather than a throwaway benchmark, at the user's direction — 281 real pages in 151 s: `--jobs 8` gives **0.537 s/page** against the 0.904 baseline, a 1.68× gain, within 24 % of the 4-concurrent-book best case. `OCR_JOBS` then raised to **12** on the user's call after the machine showed 53 % idle at 8. `OCR_JOBS = 4` → `12` is the whole change.
- 2026-09-04 — **Killing the refresh orphaned `ocrmypdf` — found by the user, fixed after the first commit.** The user's words: it must come cleanly out of Ctrl-C, that's not a question. They were right, and right that writing it up as a known gap was the wrong call: the orphan was introduced by *this thread's* `start_new_session=True`, so it was a self-inflicted regression, not a pre-existing limitation to note and defer. The child is in its own session so a timeout can kill the whole tesseract pool; the same isolation means the terminal's signal never reaches it. Now the group is killed on **any** interruption of the wait, and the wait is wrapped in a SIGTERM handler that raises, because Python's default SIGTERM handler exits without unwinding and would skip that cleanup. Verified with a real SIGINT and a real SIGTERM delivered to a real refresh, and confirmed to fail for both signals when either half is removed. Observed twice before the fix — the second time OCRing the same book as the restarted run, saturating the machine at 20 workers on 22 cores and reading as "`--jobs 12` is too high" when it was not.
- 2026-09-04 — **`nice` hides OCR from casual CPU monitors.** ocrmypdf niced its workers, so the load lands in `top`'s `ni` column, not `us`. A monitor showing user CPU only reads 2–3 % while eight cores are saturated. Cost two rounds of "why is only one CPU busy" before it was measured.
- 2026-09-04 — **tqdm ETA fixed (user-reported, outside the thread's original scope).** The refresh bar used `smoothing=0`, i.e. a whole-run average rate. On a retry pass ~46,000 of 46,400 files are skipped in seconds, so the bar jumped to ~99 % immediately and then sat for hours on a few hundred scans while reporting an ETA of minutes. Now `smoothing=0.05` (recent-rate weighted), with a `read=/skipped=` postfix updated only when a file is actually extracted, since the percentage itself is dominated by skips.
