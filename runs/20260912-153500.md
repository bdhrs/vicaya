## Retrospective
- [BEHAVIOR] Evidence: four existing vault notes attributed to the Pāḷi AN8.63 two features it does not contain — the four satipaṭṭhānas "in three modes" (*tividhena*) and the "one of two fruits — final knowledge or non-return" formula (*dvinnaṃ phalānaṃ aññataraṃ phalaṃ pāṭikaṅkhā*). Verified: `tividhena` has 2 hits in `s0305m_mul` (SN47.3) and **0** in `s0404m1_mul` (AN8.63); `dvinnaṃ phalānaṃ` has **0** in `s0404m1_mul`. Cause: see root cause below. Fix: all four corrected and re-published. Scope: global.
- [BEHAVIOR] Evidence: the error propagated by copy — the mettā note (2026-08-06) is the origin, and the karuṇā (08-07), muditā (08-08) and upekkhā (08-08) notes reproduce it verbatim, each also carrying the same "confirmed by Madhyamāgama 76 (Patton §26)" line. Cause: consecutive-day series notes copied from the previous day's note without re-verification. Fix: Suggest a series-check rule (below). Scope: global.
- [CONFUSION] Evidence: the root cause is a **shared narrative frame**. AN8.63 and SN47.3 open near-verbatim: both have a monk ask *"sādhu me, bhante, bhagavā saṃkhittena dhammaṃ desetu…"* and both receive the same rebuke *"Evameva panidhekacce moghapurisā mañceva ajjhesanti…"*. They then diverge — AN8.63 teaches the brahmavihāras → samādhi modes → satipaṭṭhāna → arahantship; SN47.3 teaches the three-mode satipaṭṭhāna. Cause: two suttas sharing an opening are trivially conflatable, and EBC lists SN47.3 as a *partial parallel* of AN8.63 — so a parallel lookup points directly at the wrong text. Fix: Suggest flagging shared-opening suttas (below). Scope: global.
- [DOC] Evidence: the note's own phrasing reveals the reversed evidentiary direction — "The Chinese parallel (Madhyamāgama 76, trans. Charles Patton, §26) **confirms**: …". The parallel was used to confirm a claim never checked against the Pāḷi. The SKILL's parallel IRON RULE is written one-directionally (do not cite a parallel *as* the target); it gives no instruction to check the target before crediting a parallel with anything. Fix: Suggest making the rule bidirectional (below). Scope: global.
- [POSITIVE] Evidence: the error was caught in a *new* run (2026-09-12 brahmavihara-insight-basis) by a source-armed reviewer with DB access, after the drafting agent had already inherited it from the old note. Cause: a reviewer that CHECKs rather than reasons. Fix: preserve; also motivates the vault-audit suggestion below. Scope: global.

## Improvement suggestions
- Suggest: make the parallel-content IRON RULE **bidirectional** in SKILL.md. Current wording only forbids citing a parallel as if it were the target (the MN21/EA50.8 case). Add the mirror clause explicitly: *a parallel's content must never be attributed to the target sutta; when a parallel is retrieved, establish separately which features are in the target and which exist only in the parallel, and record the difference as a divergence.*
- Suggest: add a **"confirms" red-flag rule**. If a draft contains a sentence of the form "the parallel confirms X" or "confirmed by <parallel>", X must already have been verified in the target text in that same run. Unverified "confirmation" phrasing is the signature of this failure class and is cheap to grep for.
- Suggest: add a **shared-opening conflation check** to Phase 2. When two suttas in the corpus share a narrative frame (identifiable by their *nidāna* + request + reply), note it, and do not treat parallel metadata as safe. Concretely: when a sutta's EBC `parallels_partial` includes another sutta that shares the same opening formula, log the hazard. AN8.63↔SN47.3 is the worked example.
- Suggest: add a **series-propagation check** to the enrichment-run and Phase 1 rules. When a factual error is found in one note of an obvious series (a dated multi-part guide, a "what the suttas say" pair, sibling retreat guides), grep the sibling notes for the same claim before closing the run. Here three siblings carried the identical error.
- Suggest: add a **vault-audit maintenance mode** — a read-only pass that takes a sutta reference and re-verifies every claim the vault makes about it, useful when a defect is discovered. Suggested trigger: any run that finds an error in a pre-existing note should offer to sweep the vault for the same claim. In this case `rg -n "tividhena|dvinnaṃ phalānaṃ"` across the vault was the whole audit.
- Suggest: record the AN8.63/SN47.3 pair as a **worked example in the SKILL's Phase 2 parallel guidance**, alongside the existing MN21/EA50.8 example, so both directions of parallel error have a canonical illustration.
- Suggest: note in SKILL.md that `dpd-db/resources/...cst/...` source XML and the SQLite tables can be queried directly to settle such disputes (e.g. `SELECT count(*) FROM s0404m1_mul WHERE pali_text LIKE '%tividhena%'` returning 0), since a count-of-zero is a decisive and cheap verification for "a feature is absent from this book".
